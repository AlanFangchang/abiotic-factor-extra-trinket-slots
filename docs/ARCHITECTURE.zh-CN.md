# 额外挂饰槽是如何实现的

[English](ARCHITECTURE.md) · [返回中文首页](../README.zh-CN.md)

本文面向希望阅读、修改或学习这个 Mod 的作者。请先用官方 Modkit 打开 `Mods/TrinketSlotProbes2QpQ`，再按文中顺序查看蓝图。`.uasset` 文件内保存了可编辑的蓝图；本文中的节点名、属性名和资源名可以直接用于查找。

## 先理解整体思路

本 Mod 没有给游戏新增一种独立的装备系统。它使用原生装备库存保存物品，再创建四个看起来像原版的槽位，将它们指向库存中新扩展的四个位置。密码盘决定哪些位置可以放入物品；挂饰效果由 Mod 根据这些位置里的物品另行协调。

```text
官方 Class Manager
  → Bootstrap：给每名玩家添加运行组件
  → State：扩展装备库存、识别密码盘、更新规则和效果
  → UI：在原版背包中创建四个槽位
  → 每个槽位：显示原生库存中对应位置的物品
```

因此，一件挂饰只有一份真实物品数据。界面不是另一份库存，也不需要只保存四个物品名称的单独存档。

## 1. 从哪里开始读

| 资产 | 作用 |
| --- | --- |
| `Class_TrinketSlotsBootstrap` | 通过官方 `ClassManager.EntityDirector` 注册启动入口。 |
| `BP_TrinketSlots_Bootstrap` | 在服务器查找玩家，为玩家补齐运行组件。 |
| `BP_TrinketSlots_State` | 管理库存容量、密码盘等级、槽位规则、Buff 和温度抗性。 |
| `BP_ExtraTrinketSlot1` 至 `BP_ExtraTrinketSlot4` | 保存每格的启用标签和放置规则，不是实际物品的第二份库存。 |
| `BP_TrinketSlots_UI` | 找到本地玩家的原版背包界面，插入四个槽位。 |
| `WBP_TrinketSlot_Runtime` | 每个槽位的外观、物品图标、提示和交互。 |

`AbioticModConfig` 和 `UUGC_Metadata` 是 Mod 配置与官方资产扫描相关配置；它们不是挂饰的自定义存储。状态蓝图直接读取当前装备的密码盘。

## 2. 启动和联机分工

`BP_TrinketSlots_Bootstrap` 在服务器运行，查找玩家角色，并在缺少组件时添加组件。State 和 UI 组件通过 `SetIsReplicated` 显式启用复制，以支持动态创建的组件。

`BP_TrinketSlots_State` 大约每 0.25 秒检查一次状态。服务器和本地控制的角色会计算与自己有关的状态；**扩容真实库存和修改挂饰效果只由服务器执行**。客户端等待库存复制，并在本地构建自己的背包界面。

组件和库存可能不会在同一时刻准备好，所以状态蓝图先检查角色的装备库存以及四个槽位组件是否有效，准备完成后才继续处理。

## 3. 物品实际存在哪里

打开 `BP_TrinketSlots_State`，查找角色的 `CharacterEquipSlotInventory`。它就是原生装备库存。服务器检查该库存的 `CurrentInventory` 长度；不足 17 格时，用 `UpdateInventorySlotCount` 扩展到至少 17 格。

| 库存索引（从 0 开始） | 用途 |
| ---: | --- |
| 7、11 | 原版两个挂饰槽 |
| 9 | 密码盘槽 |
| 13、14、15、16 | 本 Mod 的四个额外挂饰槽 |

例如，第一个额外槽的界面指向索引 13。玩家放入挂饰时，实际修改的是这个原生库存位置；取出时也是从该位置转移。原有的玩家库存存档流程负责保存物品，组件的临时缓存和界面状态则可以根据库存重新计算。

这也带来兼容性约束：如果其他 Mod 或未来游戏更新使用相同的四个索引，就可能冲突。目前没有自动分配索引或迁移物品的机制。

## 4. 密码盘怎样决定解锁数量

状态蓝图读取索引 9 的物品行名，并分别比较 `keypad_hacker_t3`、`keypad_hacker_t4`、`keypad_hacker_t5` 和 `Gatekey`。结果决定前几格处于启用状态：

| 当前密码盘 | 启用的额外槽 |
| --- | ---: |
| 未装备或低于 T3 | 0 |
| T3 | 1 |
| T4 | 2 |
| T5 | 3 |
| Gatekey | 4 |

每格的启用状态还与角色是否死亡一起判断：死亡时额外槽不再提供效果。状态蓝图把结果写入各槽位组件的标签，例如 `TrinketSlotUnlocked`，供界面判断外观与提示。

每格还会更新装备库存中对应索引的标签查询：解锁时使用 `ALL(Item.Gear)`，锁定时使用 `NONE(Item)`。前者是宽泛的装备筛选，并不等同于“只允许挂饰”；后者阻止正常物品放入。**锁定不会清空库存位置**，所以里面的挂饰仍可取出。

原生槽位控件负责装备槽的交互；Mod 另外显式检查物品是否为挂饰，用于控制可放置高亮。阅读蓝图时应区分“库存是否接受物品”和“界面是否闪烁”，不要把高亮检查当成独立的服务器放入校验。

## 5. 为什么要过滤原版装备变化事件

原生装备库存的 `AnySlotStateChanged` 会触发角色的 `CheckForGearStateChange`。在实验中，如果把额外索引 13–16 原样交给这条原生流程，它会生成装备 Actor，却无法像原生装备那样正确处理该 Actor，导致脚下出现可拾取副本。

状态蓝图只替换这一条监听：移除原有的 `CheckForGearStateChange` 委托，绑定 `TrinketSlots_FilterNativeGear`。事件来自 13–16 时不转发给原生装备 Actor 流程；其他索引仍转发给 `CheckForGearStateChange`。其他库存监听器不因这一步被移除。

这一步只阻止额外索引走不适用的装备 Actor 流程，物品本身仍在原生库存中。额外挂饰的 Buff 和属性需要下面的逻辑处理，也不会因此自动显示为角色身上的模型。

## 6. 挂饰 Buff 怎样生效和失效

每次状态更新时，蓝图读取四个额外库存位置的物品数据，拆出 `EquipmentData.BuffsWhileEquipped`：

1. 把**当前启用槽位**需要的 Buff 行句柄加入目标列表。
2. 将额外槽内物品的 Buff 纳入待核对列表，处理读档后可能残留的效果。
3. 读取原版挂饰索引 7 和 11 的 Buff；额外槽不再需要某个 Buff 时，如果原版槽仍需要它，就不移除。
4. 在服务器上移除不再需要的效果；对目标列表中的效果，只有角色尚未拥有时才调用 `Server_ApplyBuff`。

例如：T3 时第一格放入带 Buff 的挂饰，目标列表就包含它；脱下密码盘后，物品仍在索引 13，但这一格不再启用，所以对应效果会被核对并移除。重新装备密码盘后，蓝图再次将它加入目标列表。

这里按 Buff 行句柄去重，并不会让相同 Buff 因多件相同挂饰而任意叠层。它也不是通用的跨 Mod 效果所有权管理系统；与其他来源共用同一 Buff 时需要特别测试。

## 7. 抗寒和抗热为什么要单独处理

有些挂饰的效果不是 `BuffsWhileEquipped`，而是直接写在装备数据中的 `ColdResist` 或 `HeatResist`。只应用 Buff 不会自动把额外索引上的这两个值计入原生抗性，因此状态蓝图另外计算它们。

对每个成功读取、当前启用的额外槽，分别累加 `ColdResist` 和 `HeatResist`；锁定或无物品的槽贡献为 0。更新时先调用原生 `UpdateTemperatureResist` 得到原版装备基线，再加上额外槽总和，写回 `CurrentColdResist` 和 `CurrentHeatResist`。

例如，原版两个挂饰槽和四个启用的额外槽各有一件 `ColdResist = 1` 的挂饰时，原版基线为 2，额外贡献为 4，最终为 6。降级到 T3 后，额外只贡献 1，最终为 3。

蓝图缓存装备数组、上次额外贡献和上次总值；装备变化、额外贡献变化或原生总值被重算时才刷新。每次刷新都从原版基线重新计算，避免每次检查时在上一次总值上重复相加。相关属性的原生复制通知用于刷新界面并同步客户端。

当前实现覆盖抗寒和抗热，不代表直接护甲值 `ArmorBonus` 或任意伤害类型减免都已扩展。抗热的数据路径使用测试用的装备数据验证过；原版现有挂饰没有提供抗热值的实例。

## 8. 四个槽位怎样嵌入原版背包

`BP_TrinketSlots_UI` 只为本地控制的玩家处理界面，沿以下路径找到原版装备面板：

```text
GetLocalPlayerHUD
  → W_PlayerInventory_Main
  → W_Inventory_EquipSlots
  → Pane
```

蓝图建立四个指向同一个真实装备库存的网格上下文，将索引分别设置为 13–16，然后通过 `AddChildToCanvas` 将四个 `WBP_TrinketSlot_Runtime` 放进原版 `Pane`。当前每格为 84×84，X 坐标为 126.6，四格的 Y 坐标从 357.7 开始，每格增加 88。它们是原生背包面板的子控件，因此背包关闭时也会一起隐藏。

`WBP_TrinketSlot_Runtime` 基于原版 `W_InventoryItemSlot`：读取对应索引的物品和槽位启用标签，更新图标、透明度与提示；缓存物品数据以避免不必要的刷新；拾起物品时，只对符合挂饰类型要求的物品显示可放置高亮。界面操作通过原生库存引用转移实际物品。

## 9. 保存、死亡和卸载需要注意什么

本 Mod 把库存中的完整物品槽数据作为持久来源，界面和效果状态从中重建；它不需要额外的自定义存档文件。玩家死亡时，额外槽效果停止；物品是否保留、掉落或销毁还受到原版死亡设置与对应流程影响，应在目标版本中实测。

禁用 Mod 后，额外槽界面和管理逻辑也会消失。**卸载前请先取出全部额外挂饰**；目前没有在 Mod 停用后自动退还物品的机制。重新启用后能否恢复也取决于存档在此期间如何被游戏处理，不能保证所有版本和情况都成立。

本次抗性修复的测试范围和未覆盖项目见[验证记录](VALIDATION.zh-CN.md)。
